# Settlement Generator v0.1.0 — Release checklist

**Verdict:** every core workflow works in both interfaces, and every
requirement in the matrix below has automated tests. No core workflow is
known to be broken.

The release is configured for publishing:

- the updater public key is set;
- the update endpoint points at
  `github.com/Burrichen/Settlement-Generator`.

See [Before the first publish](#before-the-first-publish).

The hardening pass found and fixed several bugs; see
[Fixed in the hardening pass](#fixed-in-the-hardening-pass).

How the results below were checked:

- **Automated tests.**
  - Rust: 266 tests (core, TUI, CLI binary and Tauri shell).
  - Frontend: 60 Vitest tests.
  - Clippy with `-D warnings`, `cargo fmt`, Prettier, and the TypeScript type
    check all pass.
- **Headless screenshots** of every GUI screen:
  - both themes at 1100×720;
  - 150% zoom at the minimum window size, with a script that measures
    horizontal overflow.
- **A packaging release build** (`npm run release:build -- --packaging-test`).
  It was signed with a throwaway key that was then deleted.

Test locations used in the tables: `core/` means `crates/settlement-core/`,
`tui` means `crates/settlement-cli/src/tui/tests.rs`, and `app/` holds the
frontend tests.

### Accessibility

**GUI:**

- **Visible keyboard focus:** a 2px `--focus` outline on every control. Focus
  colour contrast is at least 8:1 on all surfaces.
- **Logical tab order:** native controls in reading order. Dialogs keep focus
  inside them and return it when they close.
- **Contrast:** every text token is at least 4.5:1, after this pass raised:
  - faint text;
  - Modern Dark's primary-button text;
  - text-field and select borders, now at least 3:1.
- **Nothing needs a mouse:** every action is a native button, radio,
  checkbox or select. The Main Menu has arrow, Home and End keys, and View
  has Up/Down plus Left/Right between the list and the actions. Both are
  covered by keyboard tests.
- **Labels:** controls carry visible or ARIA labels, and the tests find
  controls by their accessible names.
- **Scaling:**
  - Ctrl + / Ctrl − / Ctrl 0 zoom is enabled.
  - Every screen was measured at 150% zoom at the minimum window size with no
    horizontal page scroll. Wide result tables scroll inside their own pane.
  - `prefers-reduced-motion` turns off transitions.

**TUI:**

- **Nothing relies on colour alone:**
  - `▸` marks the current item;
  - `[ X ]` brackets the current choice;
  - `✓` resolved, `↺` invalidated, `·` pending;
  - `★` favourite;
  - `[x]` / `[ ]` checklist items;
  - `!` problems;
  - `(Manual only)` marks the disabled setting.

  `selection_and_choices_are_legible_without_colour` checks this.

- **Key hints:** every screen shows its keys in the footer.

### Visual polish

- No pills, gradients or oversized rounded cards remain. The only gradients
  are functional: the hatching on uncovered dice faces, and Old-Timey's faint
  page vignette.
- Removed:
  - the dashed "placeholder" box on the empty View screen, now a plain
    message;
  - unused code: a re-export, a prop, two IPC commands and an internal
    database accessor.
- Credits is still the most ornate screen. It now wraps and fits small
  windows.

### Code quality

- **No version duplication:** the workspace `Cargo.toml` is the only source.
- **No game content hardcoded in UI or engine code.**
- No TODO, FIXME or `allow(dead_code)` markers remain.
- Production `unwrap`/`expect` calls were reviewed; the remaining ones are
  checked invariants.

### Fixed in the hardening pass

- **GUI, editing:** while editing, another settlement could be picked in the
  list, and saving then renamed the wrong one. The list is now locked during
  an edit, and the edit pane is keyed to its settlement.
- **Editing, version:** an edit that only renamed a settlement re-stamped its
  "generated with" version. Now the version changes only when the results
  change.
- **Editing, unchanged saves:** both interfaces could save an unchanged edit.
  The core now refuses it, and both interfaces ask before discarding an edit
  only when it has changes.
- **Updates, unopenable data:** if the database could not be opened (for
  example after a failed upgrade), the update that might fix it could not be
  installed. The database file is now backed up directly in that case.
- **Settings:** the GUI and TUI could silently revert each other's settings
  from stale copies. Settings now save only the fields that changed.
- **Two processes upgrading at once:** the GUI and CLI opening an old database
  together could both try to migrate it, and their backups could collide.
  Upgrades now take the write lock and re-check the version, and backup names
  are reserved atomically. A stress test of 20 consecutive runs passed.
- **Small fixes:**
  - The Tauri commands now all take locks in the same order.
  - The TUI ignored keys while its "window too small" notice was showing, so
    actions could happen unseen. Keys are now paused.
  - Several errors were swallowed in both interfaces; they are now shown.
  - The tag checklist could drop unknown tags.
  - An empty generation sequence would have crashed both interfaces; the core
    now refuses it.
  - The GUI name length check counted UTF-16 units instead of characters.
- **Parity:** the TUI had a "clear stage" key and "roll rest" during edits,
  which the GUI lacks and the spec doesn't include. Both were removed.

## 2. Intentionally deferred

- **Content not yet specified.** Both are by design: generation stops with a
  readable message and lets the user choose, and nothing is invented.
  - The Size dice distribution: Size must be chosen.
  - Environment tables for setting profiles other than Kurovia.
- **Name generation:** the next minor release. **New tables:** the next major
  release.
- **Authenticode code signing** of the installer and executables. This is
  separate from update signing. Until it is done, Windows SmartScreen warns on
  first install.
- **Release automation:** no CI release workflow, so releases are built
  locally with `npm run release:build`.
- **CLI convenience:** no opt-in `PATH` entry in the installer (manual steps
  are documented). The CLI does not check for updates itself; the GUI's
  updates replace it.
- **Generated TypeScript types:** the types for core structures are kept in
  sync by hand and by tests.
- **Small duplications:** the `v` version prefix and the settlement-sheet row
  mapping are built in each interface instead of by one core view type. The
  behaviour is identical and tested.
- **Unused core methods kept as tested API:** `Database::rename_settlement`,
  `replace_snapshot` and `update_settings`. Neither interface uses them.

## 3. Known limitations

- **A running CLI during an update.** The update prompt asks users to close
  CLI windows. If one is left open, the installer cannot replace
  `settlement-generator-cli.exe` and reports that the file is in use. User
  data is unaffected, because it is backed up and closed before the installer
  runs.
- **Interim icon.** The app icon is a simple house mark, and the installer
  publisher name is Tauri's default (taken from the bundle identifier).
- **Update checks** happen at launch only. There is no "Check for updates"
  button; "Later" dismisses the prompt until the next launch.
- **Windows only** for v0.1.0. Nothing in the code prevents macOS or Linux
  builds, but they are untested.
- **Reproducibility.** The executables are reproducible (verified for the CLI
  by comparing bytes). The NSIS installer and the signatures are not, so
  checksums are published instead.

## 4. Manual release verification

### Before the first publish (done for v0.1.0)

1. The updater key pair was generated outside the repository, at
   `%USERPROFILE%\.tauri\settlement-generator.key`, **without a password**
   by choice. The key file itself is therefore the secret. **Back it up
   offline.** If it is lost, installed copies cannot auto-update.
2. `src-tauri/tauri.conf.json` has the public key and the
   `Burrichen/Settlement-Generator` endpoint.
3. Run the full check suite (root `README.md`) before each release.

### Build

4. Load the signing key into the shell only.
5. Run `npm run release:check -- --tag v0.1.0`. It must report "Ready".
6. Run `npm run release:build -- --notes notes.md`. Then clear the key from the
   shell.

### Smoke test on a clean Windows 10/11 VM, logged in as a standard user

7. The installer runs without an administrator prompt and installs to
   `%LOCALAPPDATA%\Settlement Generator`. A Start Menu shortcut is created.
8. The GUI opens on the Main Menu with `v0.1.0`.
   - Exercise both themes.
   - Change every setting, restart, and check they are kept.
9. Generate one settlement in each mode:
   - Automatic: choose the Setting Profile; when it stops at Size, choose a
     Size; finish; save it.
   - Incremental and One-table: roll some stages and choose others.

   Then:
   - Re-roll a completed settlement once.
   - Delete one unsaved settlement.

10. In View:
    - Favourite one settlement and confirm Delete is not offered.
    - Unfavourite it.
    - Edit it: a rename alone keeps "Generated with". Changing a result and
      saving updates it.
    - Cancel an edit that has changes, and confirm it asks first.
11. In Settings → View Tables and View Tags:
    - rename a table and a tag;
    - add a result and save;
    - make the dice not cover every face, and confirm Save stays disabled;
    - reset the item;
    - Restore all.
12. In a terminal, run
    `& "$env:LOCALAPPDATA\Settlement Generator\settlement-generator-cli.exe"`:
    - `--version` prints `settlement-generator-cli 0.1.0`;
    - the TUI shows the settlements, favourites, settings and content edits
      made in the GUI;
    - a setting changed in the TUI shows in the GUI after restarting the GUI,
      and a later GUI change does not revert it;
    - shrinking the window below 48×14 shows the notice and pauses keys.
13. Check that `%APPDATA%\SettlementGenerator\settlement-generator.sqlite3`
    exists, and that nothing user-related is in the install folder.
14. Uninstall with "delete app data" ticked, then reinstall: saved
    settlements are still there.

### Publish (docs/RELEASING.md, "GitHub Releases checklist")

15. Tag `v0.1.0` on the release commit. Publish a full (not pre-release)
    GitHub Release with the four files from
    `target/release/github-release/v0.1.0/`.
16. Check that `…/releases/latest/download/latest.json` shows `0.1.0`.
17. For the first update after v0.1.0 (for example v0.1.1):
    - install v0.1.0 with data;
    - publish v0.1.1;
    - on launch, v0.1.0 offers Update / Later;
    - Later dismisses it;
    - Update installs, restarts on v0.1.1 with all data, and writes a
      `pre-update-…` backup in `%APPDATA%\SettlementGenerator\backups`.
